长文本渲染压力测试

一篇刻意做长的混合内容文章，用来观察中文、英文、数学公式、表格、代码块和引用 在同一个页面上的渲染表现。

可以，这一页就专门拿来做 Edge + ChatGPT 长文本渲染压力测试。我这次故意把内容做得比较长，而且混合普通中文、英文、粗体、斜体、数学公式、表格、代码块、引用、长段落，让你观察几个东西：输入时是否卡顿、回答流式生成时是否掉帧、滚动时是否卡顿、生成结束后页面是否仍然占用很高、切换标签页再回来有没有明显延迟。

第一部分：连续中文长文本

如果单纯为了测试浏览器是否卡顿，一个比较好的办法其实不是只看回答生成的速度，因为回答生成速度里面还混杂了网络延迟、服务器流式输出速度以及模型本身生成 token 的速度。真正能够反映 Edge 页面渲染问题的，是回答已经出现很多内容以后，你开始上下快速滚动页面，或者在输入框里面连续打字，观察光标有没有延迟。比如正常情况下，即使页面已经有几万字，现代浏览器处理纯文本一般也不应该出现非常夸张的卡顿。如果只有 ChatGPT 页面卡，而其他网站、视频、PDF、网页应用都比较正常，那么问题往往不在 CPU 总体性能，也不一定在内存容量，而更可能发生在浏览器 GPU 合成、网页脚本、某个扩展程序、硬件加速、页面 DOM 数量、浏览器进程调度或者 ChatGPT 页面本身的状态上。

比如你之前说的一个现象其实很重要：CPU、内存、磁盘占用都不高，但是操作感觉依然卡。这种情况并不矛盾，因为任务管理器显示的 CPU 使用率通常是所有核心的平均值。假设你有 16 个逻辑处理器，其中一个核心被某个浏览器线程完全占满，而其他核心基本空闲，那么总体 CPU 可能只有百分之几，但负责页面交互的那个线程已经到了瓶颈。网页尤其明显，因为大量 JavaScript 和布局计算最终仍然存在主线程瓶颈。你看到 8% CPU，并不意味着网页还有 92% 的性能余量。

另一方面，GPU 也存在类似问题。浏览器页面并不是所有工作都会显示成一个明显的“GPU 100%”。Chrome/Edge 使用多个进程，包括 Browser、Renderer、GPU Process、Utility、Network Service 等。某个 renderer 出现长任务时，用户感受到的是鼠标滚动不跟手、文字输入有延迟、菜单弹出慢、窗口拖动偶尔卡一下，但 Windows 任务管理器上所有指标都可能看起来很漂亮。

所以如果现在你发现这一条回答越来越长，但滚动仍然非常流畅，那么我们就得到一个初步信息：单纯 DOM 数量或者聊天长度可能不是问题。相反，如果回答增长到某个程度以后开始明显卡，尤其是数学公式、代码块、表格出现后才开始卡，那就值得怀疑页面布局与重新渲染。

第二部分：长英文文本

Modern web applications are considerably more complicated than traditional static web pages. A webpage such as ChatGPT is not simply a document consisting of text and images. It behaves more like a desktop application running inside the browser. The browser must maintain application state, receive streaming network responses, update the document structure, perform text layout, calculate line wrapping, render fonts, process user input, handle animations, composite graphical layers, and continuously synchronize all of these operations with the display refresh cycle.

Suppose a monitor is running at 120 Hz. In ideal conditions, the browser has approximately 8.33 milliseconds to prepare each frame. At 60 Hz, the budget is approximately 16.67 milliseconds. If a JavaScript task blocks the main rendering thread for 50 milliseconds, several frames may be missed. The overall CPU utilization could still appear relatively low because only one thread is heavily occupied. Yet to the user, the interface immediately feels sluggish.

This distinction between aggregate utilization and latency is extremely important. Many people diagnose computer performance by looking only at CPU percentage, RAM percentage, GPU percentage, and disk percentage. Those indicators are useful, but they describe throughput and utilization more directly than interaction latency. A system can have enormous unused computational capacity and still feel slow if a latency-sensitive task is waiting on one serialized dependency.

For example, consider a hypothetical system with twelve CPU cores. One browser rendering thread is running at full utilization on a single core while the remaining eleven cores are almost idle. The operating system may display total CPU usage near eight percent. From a throughput perspective, most of the machine is idle. From the perspective of the web page, however, the only thread capable of performing the next required layout operation is completely saturated.

Another possibility is scheduling latency. Windows attempts to distribute workloads across cores according to priority, power policy, efficiency classes, foreground status, and numerous other factors. Modern hybrid CPUs further complicate this by including performance cores and efficiency cores. A workload that frequently migrates between cores, enters and exits low-power states, or receives unfavorable scheduling can produce intermittent latency spikes even when average CPU utilization is low.

Browser extensions can introduce additional complexity. An extension that modifies page content, inspects text, injects scripts, manages passwords, translates pages, blocks advertisements, alters appearance, or monitors network requests may execute repeatedly whenever new content is inserted into the document. A streaming AI response is unusual compared with a conventional webpage because the DOM may be updated dozens or hundreds of times while a single assistant message is being generated.

If an extension performs a complete scan of the page after every update, the computational cost may grow with the size of the conversation. Imagine that each new token triggers an operation proportional to the amount of existing text. The total amount of work can then behave much worse than a simple linear process. The page may feel perfectly normal at the beginning of a conversation and increasingly sluggish as the transcript grows.

That is one reason why testing a fresh conversation against a very long conversation is informative.

第三部分：数学公式渲染测试

普通文本相对简单，而数学公式往往涉及额外的排版。

先写一些最普通的：

$$a^2+b^2=c^2.$$

再稍微复杂一点：

$$f(x)=\int_{-\infty}^{+\infty} e^{-t^2} \cos(xt)\,dt.$$

再来一个矩阵：

$$A= \begin{pmatrix} a_{11}&a_{12}&a_{13}&a_{14}\\ a_{21}&a_{22}&a_{23}&a_{24}\\ a_{31}&a_{32}&a_{33}&a_{34}\\ a_{41}&a_{42}&a_{43}&a_{44} \end{pmatrix}.$$

再来一个极限：

$$\lim_{n\to\infty} \left(1+\frac{x}{n}\right)^n=e^x.$$

泛函分析一点：

设 \(X,Y\) 为 Banach 空间，\(T:X\rightarrow Y\) 为有界线性算子。如果

$$\dim \ker(T)<\infty,$$

并且

$$\operatorname{codim}\operatorname{Ran}(T)<\infty,$$

同时 \(\operatorname{Ran}(T)\) 是闭的，则称 \(T\) 为 Fredholm 算子，并定义 Fredholm index 为

$$\operatorname{ind}(T) = \dim\ker(T) - \operatorname{codim}\operatorname{Ran}(T).$$

再做一块更长的公式：

$$\begin{aligned} \mathcal{F}[f](\xi) &= \int_{\mathbb R^n} f(x)e^{-2\pi i x\cdot \xi}\,dx,\\ \mathcal{F}^{-1}[g](x) &= \int_{\mathbb R^n} g(\xi)e^{2\pi i x\cdot \xi}\,d\xi,\\ \widehat{\partial^\alpha f}(\xi) &= (2\pi i\xi)^\alpha \widehat f(\xi),\\ \widehat{(-\Delta)^s f}(\xi) &= (4\pi^2|\xi|^2)^s\widehat f(\xi). \end{aligned}$$

再增加一个长一点的概率表达：

$$\mathbb{E} \left[ \left( X-\mathbb{E}[X] \right)^k \right] = \int_{\mathbb R} (x-\mu)^k\,dF_X(x).$$

如果 \(k=2\)，得到方差：

$$\mu_2 = \mathbb E[(X-\mu)^2] = \sigma^2.$$

如果 \(k=3\)，可以构造偏度：

$$\gamma_1 = \frac{\mathbb E[(X-\mu)^3]} {\sigma^3}.$$

如果 \(k=4\)，可以构造峰度：

$$\gamma_2 = \frac{\mathbb E[(X-\mu)^4]} {\sigma^4}.$$

这实际上与你之前考虑的宏观经济指标问题有一点数学上的对应关系：平均收入、平均消费、平均产出等指标，本质上通常是高度聚合的统计量，而如果两个经济系统具有相同的一阶矩，它们底层分布仍然可能完全不同。例如考虑：

$$X_1\sim N(\mu,\sigma^2)$$

和另一个非高斯随机变量 \(X_2\)，即使

$$\mathbb E[X_1]=\mathbb E[X_2], \qquad \operatorname{Var}(X_1)=\operatorname{Var}(X_2),$$

也完全不能推出

$$X_1\overset{d}{=}X_2.$$

因为更高阶矩、尾部结构、分位数结构、条件分布以及时间依赖结构都可能不同。

甚至所有矩都相同，在某些情况下也未必唯一确定分布，这就涉及 Hamburger moment problem、Stieltjes moment problem 以及矩确定性问题。

Carleman 条件的一个经典形式是：

$$\sum_{n=1}^{\infty} m_{2n}^{-\frac1{2n}} = \infty,$$

其中

$$m_{2n}=\mathbb E[X^{2n}].$$

满足一定条件时，可以保证概率分布由其矩序列唯一确定。

这一段对于浏览器来说比普通纯文本复杂，因为数学公式通常需要额外排版。

import time
import math
import statistics

def artificial_workload(n: int) -> float:
    values = []
    for i in range(1, n + 1):
        x = math.sin(i) ** 2 + math.cos(i) ** 2
        values.append(x)

    return statistics.mean(values)

for size in [1000, 10000, 100000]:
    start = time.perf_counter()
    result = artificial_workload(size)
    elapsed = time.perf_counter() - start
    print(size, result, elapsed)

第六部分：随机长段落压力

为了继续增加这个页面的长度，我再连续写一些正常自然语言。

在浏览器性能分析中，有一个很常见的误区，就是把“机器够不够快”和“程序是不是有瓶颈”看成同一个问题。实际上，即使电脑性能非常强，一个存在单线程阻塞的软件仍然可以卡顿。反过来，一台配置并不特别高的电脑，只要任务比较容易并行、调度合理、渲染路径正常，也可以保持非常流畅。

例如浏览器的页面滚动有时可以由 compositor thread 独立处理，因此即使 JavaScript 主线程有一些工作，滚动仍可能保持流畅。但是一旦某些页面效果要求每一次滚动都触发 JavaScript、重新计算布局或者修改样式，就可能迫使主线程参与每一帧。这时候同样的电脑、同样的浏览器，仅仅换一个网站，流畅程度就可能完全不同。

ChatGPT 这种页面还有一个比较特殊的地方：回答不是一次性出现的，而是逐渐追加。因此前端应用需要不断接收新内容，再根据 Markdown 结构重新建立对应的元素。普通文字可能只是 <p>，代码块可能是 <pre><code>，表格会变成多个 <table><thead><tbody><tr><td> 元素，数学公式还可能生成大量 span、SVG 或其他结构。

假设一个数学公式看起来只有两行，但实际 DOM 内部可能包含很多元素。这就意味着视觉上的两千字和 DOM 意义上的两千字完全不是同一个概念。

如果一个会话里有大量 LaTeX、代码块、表格，那么页面 DOM 数量可能远高于纯文本聊天。

比如这句话很短：

$$\frac{\partial}{\partial t}u(x,t) = \Delta u(x,t)+f(u(x,t)).$$

但其浏览器内部渲染结构通常并不是一个简单字符串。

再放一个比较复杂的公式：

$$\mathcal{L}(u) = \int_{\Omega} \left[ \frac{1}{2} |\nabla u(x)|^2 + V(x)|u(x)|^2 - F(u(x)) \right]dx.$$

Euler–Lagrange 方程可能写作

$$-\Delta u+V(x)u=f(u).$$

如果研究的是非局部算子：

$$(-\Delta)^s u(x) = C_{n,s} \operatorname{P.V.} \int_{\mathbb R^n} \frac{u(x)-u(y)} {|x-y|^{n+2s}} \,dy.$$

如果研究 Sobolev 空间，可以写：

$$H^s(\mathbb R^n) = \left\{ u\in L^2(\mathbb R^n): \int_{\mathbb R^n} (1+|\xi|^2)^s |\widehat u(\xi)|^2\,d\xi <\infty \right\}.$$

甚至继续：

$$\|u\|_{H^s}^2 = \int_{\mathbb R^n} (1+|\xi|^2)^s |\widehat u(\xi)|^2\,d\xi.$$

如果此时页面滚动突然明显比上面纯文本区域更卡，就可以记一下。

第七部分：超长中文自然段

电脑“卡”其实是一个很模糊但是体验上非常真实的概念。一个人说电脑卡，可能是在说鼠标指针本身卡，也可能是窗口拖动不流畅，也可能是程序点击以后很久才响应，也可能是网页滚动掉帧，也可能是输入文字时字符出现滞后，也可能是动画帧率下降。不同类型的卡顿对应的技术原因差异非常大。

如果鼠标指针本身都卡，那一般要更多考虑系统层面的中断、驱动、DPC 延迟、USB、显示驱动甚至硬件问题。如果只是 Edge 中的 ChatGPT 页面卡，但 Windows 设置、文件资源管理器、其他网页、视频播放以及其他程序都正常，那么系统级别的问题概率就下降很多。

如果 Edge 所有网页都卡，而 Chrome 不会，那显然 Edge 本身的 Profile、扩展、硬件加速设置、实验功能或者缓存值得优先检查。如果 Edge 和 Chrome 都卡，但 Firefox 不会，那可能与 Chromium 共同组件、GPU 后端或者某个兼容性问题有关。

如果三个浏览器都只有 ChatGPT 卡，那 ChatGPT 页面自身、聊天长度、账号状态或者页面内容结构值得重点怀疑。

如果只有某一条特别长的聊天卡，新聊天完全正常，那么问题又进一步缩小到了这条聊天的前端渲染负担。

第八部分：模拟长文章

假设我们设计一个非常简化的经济系统。经济中存在 \(N\) 个家庭，第 \(i\) 个家庭收入记为 \(Y_i\)。宏观统计通常可能观察：

$$\bar Y = \frac1N\sum_{i=1}^NY_i.$$

但是显然 \(\bar Y\) 无法唯一描述整个收入分布。

考虑经济体 A：

$$Y^A=(10,10,10,10,10).$$

考虑经济体 B：

$$Y^B=(0,0,0,0,50).$$

两个经济体都有：

$$\bar Y^A=\bar Y^B=10.$$

但是结构显然完全不同。

加入方差以后可以区分这两个例子，可是即使固定均值和方差，仍然存在无穷多个不同分布。

因此可以定义一个更完整的状态：

$$\mathcal S_t = \mathcal L(Y_t),$$

即时间 \(t\) 下微观状态变量的概率分布。

传统宏观指标可以看成这个分布上的泛函：

$$M_j(\mathcal S_t) = \int \phi_j(x)\,d\mathcal S_t(x).$$

当

$$\phi_1(x)=x$$

时：

$$M_1(\mathcal S_t)=\mathbb E[X].$$

当

$$\phi_2(x)=x^2$$

时：

$$M_2(\mathcal S_t)=\mathbb E[X^2].$$

因此传统宏观经济变量可以抽象为某些测量算子：

$$\mathcal M: \mathcal P(X) \rightarrow \mathbb R^k.$$

这里 \(\mathcal P(X)\) 表示定义在状态空间 \(X\) 上的一组概率分布。

于是：

$$\mathcal M(\mu) = \left( \int\phi_1d\mu, \dots, \int\phi_kd\mu \right).$$

问题变成：

$$\mu_1\neq\mu_2$$

是否可能满足：

$$\mathcal M(\mu_1) = \mathcal M(\mu_2)?$$

当然通常是可能的。

因此宏观统计过程本质上是一种降维：

$$\text{high-dimensional distribution} \longrightarrow \text{finite-dimensional statistics}.$$

这实际上可以进一步发展成一个 inverse problem。

观察量：

$$y=\mathcal M(\mu).$$

希望恢复：

$$\mu.$$

但是如果 \(\mathcal M\) 非单射，inverse problem 就不唯一。

这与你最初思考的“宏观指标是不是只保留了低阶矩”在数学上非常接近，不过更加一般，因为你甚至不需要假设宏观指标一定是矩。

它们可以是任意 functional。

例如 unemployment rate 本身严格地说更接近：

$$U(\mu) = \int \mathbf 1_{\{\text{unemployed}\}} \,d\mu.$$

也就是说它其实是分布在某个集合上的概率质量，而不完全等价于传统意义上的一阶矩。

GDP 也不是简单的某个随机变量的均值，而是一种聚合统计。

所以如果之后真的建立纯数学理论，更准确的基础可能不是：

所有宏观变量都是低阶矩。

而是：

宏观观测量构成对高维经济状态分布的一组有限维泛函。

然后“矩”是其中一个非常重要的特例。

这样理论会更稳。

不过现在主要目的是测试卡顿，所以继续写。

第十一部分：模拟聊天长期增长

假设一条聊天已经有 300 个消息节点。

每条用户消息平均 500 字。

每条助手消息平均 3000 字。

那么粗略文本量可能达到：

$$150\times500+150\times3000 = 525000$$

也就是约 52.5 万个中文字符量级。

如果其中还包含代码、公式、表格，DOM 节点数可能远高于消息数量本身。

假设每一条消息只有 50 个 DOM nodes：

$$300\times50=15000.$$

如果复杂 Markdown 导致平均达到 200 个：

$$300\times200=60000.$$

当然这只是示意，不代表 ChatGPT 实际 DOM 结构就是这个规模。

浏览器处理几万个 DOM 元素并不是一定会卡，但是如果发生频繁的全局 style recalculation 或 layout，就可能明显影响性能。

一个更重要的问题是算法复杂度。

假设每次新增内容，某个扩展都扫描整个页面：

$$T(n)=O(n).$$

回答生成过程中新增 \(n\) 次，那么总成本可能近似：

$$\sum_{k=1}^{n}k = \frac{n(n+1)}2 = O(n^2).$$

这个差别就很大。

例如：

$$n=100$$

时：

$$\frac{100\times101}{2} = 5050.$$

而：

$$n=10000$$

时：

$$\frac{10000\times10001}{2} = 50,005,000.$$

这就是为什么某些程序会出现：

开始非常顺畅，内容一多以后突然越来越慢。

第十二部分：继续制造长度

电脑性能问题有时候特别让人烦，就是因为体感和监控指标对不上。人眼对延迟其实非常敏感。比如一个按钮正常情况下 30 毫秒就有反馈，如果突然变成 150 毫秒，人已经可以察觉。而 150 毫秒对于电脑硬件来说又并不是一个很大的时间，因此平均一分钟以后，任务管理器几乎不可能直观告诉你刚才发生了一次 150 毫秒的延迟峰值。

平均值会掩盖尖峰。

假设 10 秒时间里，CPU 延迟分别是：

$$2,2,2,2,2,2,2,2,2,302$$

毫秒。

平均值是：

$$32\text{ ms}.$$

可是用户体验会被那个 302 ms 的峰值强烈影响。

因此性能诊断里经常看 percentile。

例如：

P50 latency P90 latency P95 latency P99 latency

如果 P50 只有 5 ms，而 P99 达到 500 ms，那么平均体验可能看似不错，但每隔一阵子就会出现非常明显的卡顿。

DPC latency 也是类似。

显卡驱动、网卡驱动、音频驱动、USB 驱动等都可能造成延迟尖峰。

但是鉴于你之前描述“其他的好像都还可以，就是 Edge 用 GPT 很卡”，那么浏览器局部问题仍然比整个 Windows DPC 问题更值得优先调查。

这也是为什么我前面建议我们把问题从“电脑卡”进一步细分。

实际上可以拆成：

Windows 卡不卡？

Edge 卡不卡？

Edge 的所有网站卡不卡？

只有 ChatGPT 卡不卡？

ChatGPT 的新聊天卡不卡？

只有超长聊天卡不卡？

这种二分法比盯着任务管理器有效得多。

第十三部分：复杂公式继续压

$$\begin{aligned} E[u] &= \frac12 \int_{\mathbb R^n} |\nabla u|^2\,dx + \frac12 \int_{\mathbb R^n} V(x)|u|^2\,dx\\ &\quad - \int_{\mathbb R^n} F(u)\,dx. \end{aligned}$$

若

$$E'(u)=0,$$

形式上得到：

$$-\Delta u+V(x)u=f(u).$$

考虑线性化：

$$L_u v = -\Delta v + V(x)v - f'(u)v.$$

谱问题：

$$L_uv=\lambda v.$$

若：

$$0\notin\sigma_{\mathrm{ess}}(L_u)$$

且零特征值孤立，则可以进一步讨论：

$$\dim \ker L_u<\infty.$$

而 Fredholm 指数：

$$\operatorname{ind}(L_u) = \dim \ker L_u - \dim \ker L_u^*.$$

在适当自伴条件下：

$$L_u=L_u^*,$$

因此：

$$\operatorname{ind}(L_u)=0.$$

再考虑一个映射：

$$F:X\times\Lambda\rightarrow Y$$

满足：

$$F(u_0,\lambda_0)=0.$$

如果：

$$D_uF(u_0,\lambda_0)$$

可逆，那么根据隐函数定理，可以在 \(\lambda_0\) 附近得到：

$$u=u(\lambda).$$

满足：

$$F(u(\lambda),\lambda)=0.$$

若导数不是可逆而是 Fredholm，则可能进入 Lyapunov–Schmidt reduction、bifurcation theory 等框架。

继续：

$$X = \ker L\oplus X_1,$$
$$Y = \operatorname{Ran}L\oplus Y_1.$$

再将：

$$u=u_0+z+w$$

其中：

$$z\in\ker L,\qquad w\in X_1.$$

然后把无限维问题局部约化成有限维方程。

这里已经足够让公式排版器工作一阵了。

第十四部分：浏览器诊断的实际逻辑

如果你现在感觉“这条回答正在生成时卡，但是生成结束以后就明显流畅”，这个现象非常关键，因为它暗示增量更新本身可能是主要成本。

如果生成结束后仍然很卡，则更像是页面规模或者某个持续运行的脚本问题。

如果生成时不卡，只有滚动时卡，则偏向渲染合成路径。

如果滚动也不卡，只是输入文字卡，则偏向输入事件、页面脚本或者某个输入相关扩展。

如果输入框卡，但 DevTools Console 输入不卡，则进一步说明 ChatGPT 页面逻辑参与其中。

如果无痕窗口正常，那几乎应该优先排查扩展。

当然“几乎”不是绝对，因为无痕窗口也可能使用不同缓存、cookie、登录状态和站点存储。

第十五部分：重复长文本，继续压页面

现在继续制造一些没有特别信息价值、但可以增加页面负担的文字。

春天的天气逐渐升高，城市里的树木开始抽出新芽。街道上的人流从早晨开始增加，咖啡店打开门，公交车进入站台，路口的红绿灯按照固定的周期变化。远处的建筑物被阳光照亮，玻璃幕墙反射出天空的颜色。办公室里的人打开电脑，浏览器恢复昨天没有关闭的标签页，一些程序在后台检查更新，一些应用连接服务器同步信息。

到了中午，阳光更强，路面温度开始升高。城市的声音变得复杂，车辆、空调、行人、施工设备共同构成了一层连续的背景噪声。人在这样的环境里通常不会主动注意所有声音，大脑会自动过滤大量重复的信息，只保留重要变化。

电脑系统也存在类似机制。

操作系统、浏览器、GPU 驱动和应用程序都在不断尝试避免不必要的工作。

如果页面某个区域没有变化，理论上浏览器并不需要重新绘制整个页面。

如果某个元素被提升到独立 compositor layer，也可能只需要改变其变换矩阵，而不重新 rasterize 全部内容。

很多现代 UI 动画因此推荐使用：

transform

以及：

opacity

而尽量避免频繁修改会触发 layout 的属性。

比如：

width
height
top
left

可能更容易引发 layout。

当然现代浏览器优化很多，不能机械理解。

第十七部分：最后再塞一段长文本

如果目前你看到这里的时候页面依然很流畅，那么可以先记成“长内容本身没有立即触发严重卡顿”。接下来你把你原本想给我的那个东西发过来以后，我们可以直接在这一条会话里继续，看看随着整个对话越来越长，卡顿会不会逐渐出现。这样比单纯猜测要有用，因为我们等于在制造一个简单的可重复测试。

如果现在已经开始卡，就更加有价值。你可以特别区分三种体验：第一种是生成文字的时候卡，文字一停就好；第二种是生成结束以后滚动仍然卡；第三种是页面看起来正常，但是只要在输入框打字就卡。这三种情况对应的问题方向其实不太一样。

另外还可以试一个非常简单的操作：现在快速从页面最底部滚到最上面，再快速滚到底部。不要看 CPU，只凭体感。如果滚动动画很顺，但是输入框卡，那就是一个方向；如果滚动本身都明显一截一截，那又是另一个方向。

我再刻意写一段连续不断、没有很多 Markdown 元素的纯文本，用来和前面的公式区进行对照。如果纯文本区滚动非常流畅而公式密集区域明显掉帧，那么也可以说明不同内容的渲染成本可能存在差异。现代浏览器的文本排版虽然非常成熟，但页面上的每一个字符最终都要经过字体选择、glyph shaping、行宽计算、断行、绘制等步骤。中文字符的断行方式和英文空格断行也不完全一样。数学公式又存在自己的 layout tree。代码块可能还有 syntax highlighting。表格则需要进行列宽计算。因此同样一万字，不同结构的页面性能完全可能不同。
